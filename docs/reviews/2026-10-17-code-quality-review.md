## Summary

**What is well built.** The public surface is narrow and pinned. `historia.project` and `historia.github` re-export exactly what they should, every `__init__.py` follows the AGENTS.md rules, and `tests/test_api_submodules.py:9-49` fails if anything leaks. The project module sends every GraphQL request through one retrying poster and one response validator (`src/historia/project/_add_to_project.py:543-639`). Its transient-failure predicate is narrow, and its docstrings explain why a retry is safe rather than narrating the loop. Moved and deleted items are handled with care (`:170-242`, `:259-274`), and `_FakeGitHub` (`tests/test_add_to_project.py:49-127`) tests that behavior by what was looked up, added and rewritten instead of by call order. Source code follows the project's own conventions almost without exception. An audit of 60 functions found the keyword-only and positional-only rules applied throughout, with module-style imports everywhere. `ruff` runs with `select = ["ALL"]`, every global ignore carries a reason, and RUF100 keeps inline `noqa` honest. CI is careful: least-privilege permissions on every job, trusted publishing to PyPI, mark expressions passed through an environment variable rather than interpolated into `run:` (`.github/workflows/testing.yml:32-35`), and a version check that mirrors the AGENTS.md rule exactly. All 123 test functions carry `ai_generated`, no assertion puts the expected value on the left, every patch targets the binding the code resolves at call time, and the retry tests pin the exact backoff schedule.

**Dominant themes.**

- **The project module grew by copy and adapt.** `_add_to_project.py` is 2,031 lines. Seven queries are written once per owner type (DUP-1, about 170 lines). The token and header setup appears seven times (DUP-3), the retry loop twice in the package (DUP-2), and the end-date rule twice (DUP-4). Three functions walk the history files (DUP-5). Data passes between helpers as a six-tuple and as dict bags whose types are erased and then restored with 11 casts, which also hides two guards that can never fire (CON-1, CON-2, DC-1).
- **Tooling configuration has drifted from what it governs.** Two pre-commit hooks can never run, one because it points at the deleted `action/` directory and one because of a file-extension typo that left the Read the Docs config unvalidated (DC-4, CL-12). Several settings have no effect (DC-7, DC-8, DC-9, DC-11, DC-12). `hatch-vcs` is installed by every build and never used (DC-10). black targets Python 3.12 for a 3.10 package (CL-14), and ruff's `exclude` silently drops its default excludes (CL-15).
- **The tests follow the rules but repeat their scaffolding.** About 80 mocked responses are hand-built (DUP-12), and several groups of tests differ only in literals (DUP-10, DUP-11, DUP-13, DUP-14). A few tests check less than they claim: two assert nothing, and the in-memory GitHub fake answers unmodeled operations with success (CL-8, CL-10, CL-18).
- **Docstrings and comments have drifted.** A public docstring documents a return value that does not exist (CL-1), several say the opposite of the code beside them (CL-2), and the comments that narrate code predate the AGENTS.md rule against them (CL-3).

**Needs verification soon.** NV-7 is the most serious. When an item's Members value lies beyond its first 20 field values, `populate --members` overwrites the stored text, which loses data silently. NV-1 and NV-2 describe rate-limit handling that keeps sending requests after GitHub has said stop. NV-12 shows that on a machine east of UTC the two-day refresh can miss a day's events for good. NV-3 shows that a failure partway through `historia project create` leaves an orphan project. NV-18 notes that the only end-to-end integration test is skipped in every CI run.

No security-sensitive findings were found, so nothing is withheld.

- **Location**: `src/historia/data/github/_update.py:31`, `:35-38`, `:49`, `src/historia/_cli.py:50-54`, `src/historia/data/github/_fetch_info.py:247-256`
- **Observation**: `update()` takes "today" in the local timezone, as its help and docstring say. The fetch side matches GitHub's UTC timestamps by string prefix, and the project side cuts off in UTC. On a UTC+N machine one of the two refreshed days is a future UTC date, and the real "yesterday" in UTC falls outside the two-day overwrite window, which the tutorial (index.md:37) promises to refresh. A mocked run under `TZ=Pacific/Auckland` reproduced the shift. The documented GitHub Action runs in UTC and is unaffected. Each side was chosen in a separate PR (#58 and #183) and neither records a decision about which calendar defines a day.
- **Why it is not a quality change**: The default dates `historia update github` fetches would change on non-UTC machines.
- **Decision needed**: Which calendar defines a day. Anchoring on UTC and saying so in the help is the smaller change.

#### NV-13 — `--recency` help says "N most recent days", but both commands cover N+1

- **Location**: `src/historia/_cli.py:37-43`, `:230-241`, `src/historia/data/github/_update.py:27-28`, `:41`, `src/historia/project/_add_to_project.py:1097-1105`, `:1178-1182`
- **Observation**: `update()` iterates `range(past_number_of_days + 1)` and its docstring says "in addition to the anchor date". The project cutoff is `today - N` and inclusive. Both behaviors are pinned by tests (`tests/test_dump/test_graphql_api_dump.py:209-216` and `tests/test_add_to_project.py:1669-1675`), but the `--help` text describes N days.
- **Why it is not a quality change**: Only the `--help` output changes, but it is user-visible.
- **Decision needed**: Confirm the arithmetic is the contract and reword the help, for example "Number of past days to fetch, in addition to the anchor date".

#### NV-14 — Negative `--recency` or `--placeholder`, and a same-status transition, are accepted silently

- **Location**: `src/historia/_cli.py:37-43`, `:133-144`, `:218-241`, `:293-307`, `src/historia/project/_add_to_project.py:1989-2031`
- **Observation**: The options are plain `type=int`. `update github --recency -5` is a silent no-op with exit code 0. `--placeholder -30` writes an End date before the Start date onto a shared board. `transition --status Done --new Done` rewrites every Done item.
- **Why it is not a quality change**: Invocations accepted today would exit with a usage error.
- **Decision needed**: Whether to use `click.IntRange(min=0)` and reject or skip a same-status transition.

#### NV-15 — `update_project_item_members` breaks the single-parameter rule in the public API

- **Location**: `src/historia/project/_add_to_project.py:1215`, `:1920`, `src/historia/_cli.py:274`
- **Observation**: AGENTS.md requires `/` for single-parameter functions. `update_project_item_members(*, project_url)` is keyword-only, while its sibling `get_project_closing_workflows(project_url, /)` follows the rule. The function arrived in v0.10.5, after the rule (v0.10.2), with no recorded exception. The click callback that calls it must stay keyword-only, which is fine.
- **Why it is not a quality change**: `update_project_item_members(project_url=...)` would raise `TypeError`, a breaking change to the public API, and AGENTS.md forbids compatibility aliases.
- **Decision needed**: Whether the style rule outweighs API stability for this function.

#### NV-16 — Warning stacklevels are hand-picked and none reaches the caller's code

- **Location**: `src/historia/project/_add_to_project.py:118`, `:242`, `:315-318`, `:447`, `:494`, `:626`, `:1047-1050`, `:1158-1163`, `:1245-1248`, `src/historia/project/_create_project.py:65`, `src/historia/data/github/_fetch_info.py:301`
- **Observation**: Every public function is wrapped by `@beartype.beartype`, which adds a frame. A probe that triggered all 11 sites found the warnings attributed either to the beartype wrapper pseudo-file or to lines inside historia, never to the caller. Several helpers are reached at different depths, so no constant value is right, and `skip_file_prefixes` needs Python 3.12. This also blocks one duplication fix. The five `_list_project_*` functions repeat one pagination loop, and any shared helper adds a frame that moves the 403 warning from the command to the list function.
- **Why it is not a quality change**: The file and line printed with each warning, and which `filterwarnings(module=...)` rules match, would change.
- **Decision needed**: Whether warning attribution matters. If it does not, record that, and the pagination loops can then be shared.

#### NV-17 — `_get_owner_node_id` reports any failure as a wrong login

- **Location**: `src/historia/project/_create_project.py:162-186`
- **Observation**: Any non-200 from `/users/{owner}`, including a 401 for a bad token or a 403 rate limit, falls through to `/orgs/{owner}` and then raises "Please verify the login is correct." REST `/users/{login}` is believed to answer for organizations too, which would make the `/orgs/` branch reachable only after a failure that hits it as well. That could not be verified here. The tests always return 200, so none of this is covered.
- **Why it is not a quality change**: The error type, the message and the number of GETs would change.
- **Decision needed**: Confirm the REST behavior, then raise the "verify the login" error only on 404 and report other statuses as they are.

#### NV-18 — The remote integration test never runs in CI

- **Location**: `tests/test_add_to_project_integration.py:17-19`, `:97-106`, `.github/workflows/testing.yml:11-35`, `daily_tests.yml:17-23`, `testing_pr.yml:15-24`
- **Observation**: The only `remote`-marked test function is skipped unless `RUN_INTEGRATION_TESTS=1`, and no workflow sets that variable. The remote jobs therefore always report it skipped, and the 160-line file gets no CI execution.
- **Why it is not a quality change**: Enabling it makes the remote jobs add and delete a real item on the live project board, which the tutorial suite already mutates. Deleting it removes the only end-to-end check of `add_to_project` against the real API.
- **Decision needed**: Enable it, delete it, or record why it is manual-only.

#### NV-19 — Tests import 18 private helpers that have no public path

- **Location**: `tests/test_add_to_project.py:12-30`, `tests/test_collect_unique_urls.py:6`, `tests/test_add_to_project_integration.py:11`
- **Observation**: 38 of the 65 tests in `test_add_to_project.py` call a private helper directly, and lines 416-427 assert that two private helpers are positional-only. AGENTS.md says to "avoid importing private API" in tests. Its second sentence, "import from what is publicly exposed", presupposes a public path, which none of these helpers has. The maintainer still accepts the practice: #195 added a test that calls `_add_item_to_project` directly.
- **Why it is not a quality change**: Rewriting the tests through the public API would change what they pin, such as member normalization and the retry schedule.
- **Decision needed**: Whether to amend AGENTS.md to say white-box tests of helpers with no public path are allowed. That is the cheap option, and CL-7 handles the helpers that do have a public path.

#### NV-20 — Python versions disagree across tooling, and CI tests only 3.13

- **Location**: `pyproject.toml:25`, `:35-39`, `:71`, `:157`, `.pre-commit-config.yaml:7-8`, `.github/workflows/testing.yml:24-27`, `release_pypi.yml:22-25`, `containers/Dockerfile.dev:1`, `containers/Dockerfile.latest:1`, `docs/.readthedocs.yaml:6`
- **Observation**: The package claims 3.10 through 3.14. mypy and ruff target 3.10, black targets 3.12 (CL-14), the hooks run on 3.11, and CI, the release, Read the Docs and both images use 3.13. The only test job runs 3.13, so neither the floor nor the ceiling is exercised. CHANGELOG v0.10.15 (#179) records a 3.10-only break that shipped because nothing ran 3.10.
- **Why it is not a quality change**: A test matrix adds CI jobs that can fail.
- **Decision needed**: Which versions are supported. Then align the classifiers, a matrix in `testing.yml` (with Codecov and the remote run limited to one version), and `default_language_version`.

#### NV-21 — The release image installs whatever PyPI serves, not the tagged tree

- **Location**: `containers/Dockerfile.latest:6`, `.github/workflows/build_and_upload_docker_image_latest.yml:39-52`, `:79-80`
- **Observation**: The workflow tags the image with the version in the checked-out `pyproject.toml`, and its comment and CHANGELOG v0.11.1 (#184) say the image "is built from the tree at that tag". `Dockerfile.latest` runs an unpinned `pip install historia` and never reads the context, so right after a release the index can still serve the previous version under the new tag. The smoke test runs `--help`, which cannot catch a mismatch.
- **Why it is not a quality change**: Pinning `historia==<version>` makes the build fail, rather than publish a mis-tagged image, when PyPI has not caught up.
- **Decision needed**: Pin with a build argument and a wait or retry, or build from the checked-out tree as `Dockerfile.dev` does. Smoke-test with `--version`.

#### NV-22 — The "Test dev container" workflow never runs the image it builds

- **Location**: `.github/workflows/build_and_upload_docker_image_dev.yml:1`, `:12`, `:28-47`
- **Observation**: The workflow and job are named for testing, but the steps only build, log in and push. The release workflow does run its image (`latest.yml:79-80`). A broken entrypoint or console script would pass on a pull request and be pushed as `:dev` on merge.
- **Why it is not a quality change**: It adds a CI gate that can fail.
- **Decision needed**: Whether to add the same two-line `Smoke test image` step after the build.

## Not changed (deliberately)

These looked like findings and are not, either because they are load-bearing, because the project chose them on purpose, or because an adversarial check showed the change costs more than it saves.

**Documented or load-bearing choices**

- **The public `historia_data_update_cli` name** (`src/historia/_cli.py:28-30`). It lacks the underscore its sibling groups carry because CHANGELOG #38 exposed it "for plugin-oriented extension". Renaming it would break plugins.
- **The tutorial conftest's own retry, GraphQL and header helpers** (`docs/tutorial/conftest.py:24-115`). AGENTS.md keeps tests off private API, and #205 added the copy on purpose. DUP-2 leaves it alone.
- **The different retry predicates in the fetch and project modules.** CHANGELOG v0.12.2 documents that only the project commands retry GitHub's generic 200 error.
- **Treating HTTP 403 as a rate limit.** Public docstrings, the CLI message and tests (`tests/test_api_fetch.py:39-57`, `tests/test_add_to_project.py:665-677`) all pin it, back to #6. A 429 or a 200 `RATE_LIMITED` payload raising loudly is fail-safe.
- **The search design in `_fetch_info.py`.** The opened-item searches stop at 100 per day by a stated assumption (line 226). `timelineItems(last: 100)` was raised from 20 on purpose in #200. The `updated:>=` candidate search is documented in #189 and the docstring.
- **`prs_review_requested` recording only pending requests.** Issue #199 designed it so, with `prs_reviewed` catching requests once fulfilled.
- **The two-day overwrite window** (`_update.py:49`). The tutorial documents it ("The two most recent days are always refreshed").
- **Not writing empty results** (`_dump.py:62-63`). It is deliberate and tested (#68), and deleting a file on an empty overwrite would turn a transient empty search into lost history.
- **`update members` replacing rather than merging Members.** It recomputes from GitHub like `update dates` does, `populate --members` re-merges the history usernames, and merging would make a removed assignee impossible to drop.
- **Detecting closing workflows by the "auto-close" substring.** CHANGELOG v0.10.11 chose it and tests pin it. Only the `first: 20` cap is reported, in NV-7.
- **The `NOT_FOUND` tolerance applying only to date updates.** #105 scoped it to `update dates` on purpose.
- **Settings that restate their tool's default** (withdrawn DC-6). These are `default_install_hook_types: [pre-commit]` (`.pre-commit-config.yaml:4-6`), `fixable = ["ALL"]` (`pyproject.toml:123`) and `known-first-party = ["historia"]` (`pyproject.toml:154`). The maintainer states defaults explicitly on purpose. An explicit value is easier to read and does not change silently if a tool changes its default.
- **Lint and type-check fixtures that look redundant.** Every inline `noqa` is still needed (RUF100 is on). Every global and per-file ruff ignore except those in DC-8 and DC-9 still fires. `relative-imports-order` is load-bearing. The `typing.cast` calls at `_add_to_project.py:163` and `:188` and in `tests/test_add_to_project.py:418` and `:425` are needed by mypy. The long `datetime.datetime.now(tz=...).astimezone().date()` is the DTZ011-compliant spelling.
- **Signatures imposed by frameworks.** Click invokes callbacks with keywords, so `_historia_project_update_members_cli(*, project_url)` must stay keyword-only. Sphinx calls `_substitute_historia_action_tag` positionally, so it cannot be keyword-only. Single-parameter framework callbacks in `docs/` could take `/`, but the project does not shape callbacks to the rule elsewhere.
- **CLI flag names differing from keyword names** (`--recency` for `past_number_of_days` and so on). AGENTS.md asks for exactly that.
- **`tests/test_cli.py` importing `historia._cli`.** AGENTS.md's monkeypatch rule requires patching the importing module's binding, which here is private.
- **The fake `GITHUB_TOKEN` set in the dump tests.** Those tests never read it, but CI exports a real token, so the fake guards against a mis-targeted mock calling the live API with CI credentials.
- **`.gitignore` without cache directories, `build/` or `*.egg-info`.** pytest, ruff and mypy write their own `.gitignore` inside their caches, and hatchling never writes `build/` or egg-info.
- **`[tool.hatch.build.targets.wheel] packages`**, `sys.path.insert` in `docs/conf.py`, `functools.cache` on `_format_graphql_queries`, `node.get("enabled") is True`, and the golden files under `tests/test_dump/expected_dumps/`. Each is inert-looking but used or a reasonable guard.

**Real, but not worth a change on its own**

- **Inlining `_normalize_member_value`** (`_add_to_project.py:387-389`). The name says what an empty-set merge means, and inlining needs a named local to stay readable.
- **The redundant parentheses around five GraphQL templates in `_fetch_info.py`.** black's preview style adds them, so if anything the bare `prs_opened` entry is the outlier.
- **`importlib.metadata.distribution("historia").version`.** It is documented public API and equivalent to `importlib.metadata.version`. No project rule prefers either.
- **Merging the two "status option not found" blocks in `transition_status`** (`_add_to_project.py:1989-2003`). After the project's own formatting the helper adds lines, and neither error path is tested.
- **Building error messages lazily or sharing the "failed!" header.** The project prefers messages written out at the raise site (the TRY003 comment), and the gain is negligible.
- **Folding `_set_item_status`, `_set_item_date` and `_set_item_text` into one setter.** Their error contracts differ on purpose (#105), and the merged helper needs a dispatch table and a `noqa`.
- **A `REQUEST_TIMEOUT_SECONDS` constant and a GraphQL URL constant.** The project's PLR2004 comment prefers small literals inline, and the URL repetition largely disappears with DUP-2.
- **A decorator for the CLI error handling.** With the required annotations it made `_cli.py` longer. DUP-9's context manager is line-neutral.
- **Removing the `shellcheck` hook.** It has never had a file to check, but it costs nothing and reads as a guard for future scripts.
- **Making `[tool.mypy] files` match the hook.** The only documented mypy run is pre-commit, which honors `python_version` and passes files explicitly. Bare `mypy` reports 11 missing-stub errors, which is worth knowing but not a defect in the documented workflow.
- **The unmatched Codecov `ignore` entries** (`.github/.codecov.yml:17-19`). The file is outside this review's scope, and the entries are a standard guard if coverage scope widens.
- **Removing the S108 ignore by rewriting two `/tmp` literals.** The ignore is documented and any `pyproject.toml` edit forces a release bump.
- **Atomic writes for history files.** The documented deployment commits the data repository only after a successful run, so a truncated file never persists.
- **Calendar validation of `date` and validation of `username`.** The CLI path already parses dates, and a user can only change their own query.
- **Calling `_parse_project_url` once per command, a `_ProjectRef` tuple, a `NamedTuple` for `existing_items`, folding `get_project_closing_workflows` into its private helper, and generating the six fetch query templates.** Each adds churn or hides a literal that tests assert, for no removed branch.
- **Test refactors that save nothing.** An autouse `GITHUB_TOKEN` fixture would overwrite the real token the integration test reads. Merging the four `*_raises_without_token` tests, the nine type-check tests, the three `test_create_project.py` tests, or the dump path layout either adds lines or loses descriptive names. One shared `CliRunner` saves a line per test against a conventional idiom. The fallback at `tests/test_add_to_project.py:2205` keeps the test agnostic to how `tqdm` is called. The JSON-string parameters in the dump overwrite test fail loudly if they drift.
- **Sharing `_bad_gateway_response` between `tests/test_api_fetch.py` and `tests/test_add_to_project.py`.** The two six-line helpers are identical, but `tests/` is deliberately not a package and has no shared module, so the first helper module would cost more than it saves.
- **Moving the positional `side_effect` workflow tests onto `_FakeGitHub`.** Several call-count assertions are the contract under test, such as proving that unchanged members cause no writes, and the fake would need far more modeling first.
- **Removing the duplicated `github` export row and `update --help` check** (`tests/test_api_submodules.py:14`, `:33`, `tests/test_cli.py:39`, `:122`). Each sits in a separately named contract, top-level versus submodule exports and group help versus command presence. One verifier recommended deleting the row and another rejected it, so it stays.
- **Sharing helpers between the integration test and the tutorial conftest.** The integration test never runs (NV-18), and sharing them needs a new module plus a `pyproject.toml` change.

## Method & limits

**Scope.** In scope were `src/historia/**/*.py` (about 3,500 lines), `tests/**/*.py` (about 4,000 lines), `docs/conf.py`, `docs/tutorial/conftest.py`, `pyproject.toml`, `.pre-commit-config.yaml`, `.github/workflows/*.yml`, `.github/dependabot.yml`, `containers/Dockerfile.*`, `docs/.readthedocs.yaml` and `.gitignore`. `CHANGELOG.md`, `README.md`, the tutorial and other docs pages, and `AGENTS.md` were read for intent only. The golden files under `tests/test_dump/expected_dumps/` were out of scope.

**Execution.** The review ran in a throwaway cloud container on a fresh clone. No command wrote into the repository, and `git status --porcelain` stayed empty apart from this review's own commits. Every experiment that needed an edited tree ran on a `git archive` copy in a scratch directory. `api.github.com` was not reachable from the container, so the 17 tests marked `remote`, the tutorial examples, and every claim about live GitHub behavior are marked as unverified where they matter.

**How findings were produced.** The skill's mechanical sweep fed eight independent finder agents, one per lens: dead code, inert configuration, duplication in source, duplication in tests, consolidation, cleanup, test conventions, and needs-verification. Each finder read its files in full and returned candidates with locations, evidence and a proposed change. Two adversarial verifiers then checked every candidate. A trace verifier re-read each cited line, searched for every reference including string patch targets, and ran the change on a scratch copy where it could. An intent verifier read `git log -S`, `CHANGELOG.md`, AGENTS.md and inline comments to find deliberate choices, and weighed cost against benefit. The verifiers reviewed 125 candidates. A candidate became a finding only if the trace verifier confirmed it. Anything either verifier showed to be deliberate, or not worth its cost, moved to "Not changed (deliberately)", and anything whose fix changes behavior moved to Needs verification. Overlapping candidates from different lenses were merged into one finding per root cause. The synthesis, the merging and the final wording were done by hand from the verifiers' reasoning. The run was interrupted twice, by a container restart and a usage limit, and resumed from cached results, so no candidate went unverified.

**What could not be verified.** Live GitHub behavior, such as whether REST `/users/{login}` answers for organizations (NV-17) and how GitHub reports review requests (NV-10). The remote integration test and the tutorial examples. Docker builds, because no daemon was available (DC-13, CL-17, NV-21, NV-22). The history is a shallow clone grafted at 65f4748, so `git log -S` could not date anything older, and CHANGELOG entries were used instead.

**Commit drift during the review.** The review started at e37c97a. This branch then added 366e365, which changes only `docs/conf.py:70` to exclude `docs/reviews/` from the Sphinx build. Every line cited in this report is identical at both commits, and no finding is affected.

**Security-sensitive findings.** None were found, so nothing is withheld. The workflows reference secrets by name only.

**Where this report lives.** `docs/reviews/2026-10-17-code-quality-review.md`. The repository had no reviews directory, and the request named `docs/reviews/`, so the next run should use that directory rather than the skill's default `docs/code-reviews/`. Sphinx treats every Markdown file under `docs/` as a page and Read the Docs builds with `fail_on_warning`, so 366e365 excludes the directory from the docs build.
